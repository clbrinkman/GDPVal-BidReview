# 标书审查 Benchmark 数据治理平台（prototype）

对标 OpenAI GDPval 的思路，做一个**审查类** benchmark：让模型审查投标文件，检出其中被注入的偏差。
由于真实标书不公开，采用**注入式合成**：抓取真实招标文件 → 程序化/生成式构造合规基线标书 → 注入已知偏差 →
偏差自带 ground truth（before/after/位置/期望检出结论），评测检出率与误报率。

本仓库是其中的**数据治理 + 后期人工工作台** prototype，覆盖 选题（爬虫）→ 构造（注入）→ 质检（人工校验）闭环中
"人"的那一环，设计目标是**尽可能少的人工**：能走规则的不进人工队列，必须人工的做成 <30 秒可判的自描述卡片。

运行：`python platform/app.py` → http://127.0.0.1:8321 （Python 3.13，依赖 fastapi / uvicorn / requests / bs4 / lxml）

## 已实现功能

- **爬虫选题**：ccgp 公开招标频道抓取（48 项目/26 附件），URL 去重幂等，TDR 统一编号
- **项目总览（标注入口）**：类别卡（工程/货物/服务）→ 项目 → 三类标注任务，实时待审数；
  分类走关键词规则（剥代理机构名前缀，命中词可溯源），不设人工
- **生成节点审核**：N1 输入解析 → N2 基线合规 → N3 偏差注入 → N4 成稿质量，任一驳回即回炉
- **专家校验**：law/scheme/plaus/inj 四区，点选绿色高亮 + 上一条/暂存(draft)/提交/下一条
- **规则标注**：rubric 条目保留/改写（文本直接写回）/删除，同款暂存/提交交互
- **规则编辑**：rubric 库、条目编辑、模板绑定多项目
- **环境文件**：噪声环境展示（含证据绿/噪声红/普通灰）+ PDF 阅读器（原生渲染兼容扫描件，按页反馈）
- **辅助队列**：GT 校验（gt_status 状态机）、finding 裁决、附件校准
- **治理**：六前缀编号、五类错误法典、全部判定可撤销回退、暂存/提交两态、schema 迁移 V1-V8
- **演示数据**：5 case / 59 校验项 / 34 环境文件 / 44 rubric 条目 / 4 注入 GT，开箱即用

## 设计理念

### 1. GT 免费：注入式合成，答案是我们自己埋的

**问题**：做审查 benchmark 需要"错标书 + 正确答案"的对照数据，但真实投标文件涉及商业秘密永不公开，
公开渠道只有招标文件（招标方视角），拿不到投标方视角的真实错例。

**反转**：与其找不到错，不如自己造错。抓真实招标文件 → 构造合规基线标书 → 注入已知偏差。
偏差是我们埋的，所以每条 GT 天然自描述五要素：注入位置（locator）、改前文本、改后文本、
期望模型检出的结论、错误类型码。

**对人的意义**：标注者不"找答案"，只"验答案"——对着改前/改后 diff 判断"这个偏差成不成立、像不像真的"，
单条目标 <30 秒。这是整个平台能把人工成本压到最低的根本。

### 2. 后期人工，不是采集人工

标注人力是 pipeline 里最贵、最不可扩展的资源（GDPval 级成本主要来自专家时薪）。
因此平台严格区分两类工作：

- **确定性工作 → 走规则，不设人工队列**。项目分类、招标文件识别这类有确定答案的事，
  做法是"标定小样本 → 写规则 → 测规则准确率 → 撤人"。规则命中依据在 UI 上可溯源
  （如分类展示"规则命中『车辆』"），规则错了改规则，不养长期人工。
- **机器原理性做不了的判断 → 才进人工**，且只有三个位置：
  ① 审核生成的标书是否符合要求（节点审核）② 修改调整规则（规则标注/编辑）③ 质检（专家校验）。

### 3. 两层 rubric：template + delta，评分永不跨 rubric 合总分

不同项目的评标办法异构——工程看资质和工期，货物看参数应答，服务看方案和业绩，
把它们的分数加总比较没有统计意义。但同类项目的条款大量同构（资格五条、通用废标条款家家都有）。

所以 rubric 分两层：`template` 层沉淀通用审查项（可绑定多项目复用），
`delta` 层从每个项目的需求文档解析专用项。评测指标永远**逐条**（某个错误类型的检出率/误报率），
按 错误类型 × 项目类别 宏平均切片，且只在同版本 case_set 上比较。

### 4. 噪声环境：测的不只是判断，还有取证

真实审查员面对的不是一份干净的标书，而是一个塞满旧版文件、无关资料、扫描件的文件夹。
把被测 agent 放进同样的噪声环境里自行取证，benchmark 才能测出"找证据"的能力而不只是"下判断"的能力。

环境文件带三种标记：角色（招标文件/标书/证明材料/信用查询/澄清函/旧版噪声/无关噪声）、
`has_evidence`（是否含注入偏差的证据 → 测取证召回的 GT）、`is_scan`（扫描件 → 测 OCR 鲁棒性）。

### 5. 状态机治理：数据资产可回溯、可撤销、永不静默覆盖

数据集会经手多人多轮：编号只增不改不复用；状态单向流转
（GT：auto → needs_review → confirmed|rejected；case：baseline → injected → evaluable|retired）；
人工判定分"暂存"（draft，可反悔）与"提交"（result，可撤销回待审）两态；
评测 run 永不覆盖，指标只在同版本 case_set 上可比。

## 节点审核详解

标书生成是一条流水线，**错误越晚发现越贵**：N1 解析错了，后面全错；
基线不合规，注入就失去参照系。所以审核按生成关键节点设卡，每个节点产出物不同、给人看的证据也不同。
任一节点驳回 = 该 case 回炉到对应环节重做，四节点全通过才进题库（evaluable）。

| 节点 | 生成侧做什么 | 人工审什么（证据） | 驳回意味着 |
|---|---|---|---|
| **N1 输入解析** | 从招标文件解析资格要求、商务条款、实质性条款 | 抽取是否完整准确：资格项漏没漏、★条款识别对不对、原文定位能不能对上 | 重新解析输入 |
| **N2 基线合规** | 生成一份"本应通过审查"的基线标书 | 基线必须本身合规：报价≤预算、期限/有效期满足、资格材料齐全。基线带错，注入偏差就测不出模型真本事 | 重新生成基线 |
| **N3 偏差注入** | 按错误法典注入偏差并生成 GT | 注入是否成立（改后文本真的构成该错误）、GT 期望结论是否正确（在 GT 校验队列进行） | 重新注入 |
| **N4 成稿质量** | 输出最终标书成稿 | 成稿像不像一份真标书：章节完整、全文一致（报价/名称多处出现一致）、无占位符和模板残留 | 成稿重修 |

审核卡形态：证据原文（解析结果/条款对照/diff）+ 通过/驳回 + 驳回原因。
驳回原因留痕（琥珀色备注卡），回流给生成侧当返工依据。

## 专家校验详解

四类判断机器**原理性**替代不了（不是"暂时做不了"，是做了也不可信），必须领域专家：

| 校验区 | 为什么机器做不了 | 判定选项 |
|---|---|---|
| **law 法规引用真实性** | 生成模型会编法条——真实法号配错误内容、已废止条文照引。需要法规库知识和时效判断，且判定错了污染整个 case | 存在且现行 / 存在但已废止 / 编造不存在 / 场景不适用 |
| **scheme 方案答非所问/矛盾** | 跨章节语义一致性：参数应答表承诺"≥600L 满足"，方案正文写"主流机型 300~500L"——字符串比对发现不了，要理解"应答承诺"与"方案描述"的语义冲突 | 无矛盾 / 应答表与方案矛盾 / 答非所问 / 漏项 |
| **plaus 虚构事实合理带** | 构造的投标人、业绩、团队规模是虚构的。太假→模型一眼识破，测不到真本事；太真→触碰伪造风险。"合理带"是纯粹的行业经验判断 | 合理 / 偏假但可接受 / 一眼假需回炉 |
| **inj 注入偏差领域可信度** | 注入的偏差必须像真实投标人会犯的错（与真实废标案例分布对齐），否则模型学到的是"我们的注入习惯"而不是真实错误模式 | 自然 / 可疑但可判 / 不像真实偏差 |

**交互设计**（每处都在防误操作、保连续作业）：
- **点选 ≠ 提交**：verdict 按钮只改绿色高亮选中态，避免误触直接落库；
- **暂存**：查证到一半要离开，选中的 verdict + 备注存 draft，回来接着干，卡片显示"暂存中"；
- **提交**：未点选时不放行；提交后仍可「↩ 撤销」回待审；
- **上一条 / 下一条**：锚点跳转连续作业，不用回列表翻页。

## 规则标注详解

rubric 条目是从需求文档**解析**出来的（规划：OpenBidKit 18 解析项 schema 自动抽取），
而解析会犯四类错：**漏抽**（条款没抓到）、**误抽**（把说明性文字当条款）、
**粒度错**（一条拆成多条或多条并成一条）、**归类错**（废标条款归成打分项）。
解析产物不经过人，错误会直接变成评分标准，污染下游所有 case——所以条目必须过人。

三个判定就是三种处置：

- **保留**：解析正确，条目进库可用；
- **改写**：条款抓对了但表述不准（漏了"原件扫描件"、金额没带上），直接在卡片上改文本，
  提交后**写回 rubric_item**——标注动作本身就是修正通道，改完即新规则，不用跳转编辑页；
- **删除**：误抽或对本项目不适用的条目，标记剔除（软标记留痕，不物理删除）。

与"规则编辑"的分工：标注管**质检**（这条该不该在、写得对不对），
编辑管**治理**（条目结构、层归属、模板绑定哪些项目）。

## 专业词表

| 词 | 含义 |
|---|---|
| **tender / TDR** | 招标项目（爬虫抓取的公告+附件），平台一切实体的根 |
| **rubric / RBC** | 审查规则集。模板 rubric 可绑多个项目；项目 rubric 从需求文档解析生成 |
| **rubric_item** | 单条审查/打分项，分 `template`/`delta` 两层，类别：qualification 资质 / compliance 符合性 / rejection 废标条款 / score 打分项 |
| **case / CASE** | 一份构造的投标标书案例，属于某 tender 的某变体（如 A01/A02） |
| **injection / INJ** | 注入的偏差，自带 GT。构造方式 `P` 程序化 / `G` 生成式 / `R` 真实案例 |
| **err_taxonomy / ERR** | 错误类型法典：`QUA` 资质 / `FMT` 格式 / `SUB` 实质响应 / `PRC` 报价 / `DOC` 文档，code 只增不改 |
| **生成节点 N1-N4** | 标书生成的关键审核点：N1 输入解析 → N2 基线合规 → N3 偏差注入 → N4 成稿质量 |
| **专家四区** | 机器替代不了的判断：law 法规引用真实性 / scheme 方案矛盾 / plaus 虚构合理带 / inj 注入可信度 |
| **review_check** | 一条人工校验项（节点审核或专家校验），可暂存/提交/撤销 |
| **env_file** | 环境文件：agent 取证评测的噪声环境，角色 tender/bid/cert/credit/clarify/noise_old/noise_misc |
| **GT** | ground truth。`gt_status` 状态机：auto → needs_review → confirmed / rejected |
| **检出率 / 误报率** | 评测指标：hit/miss/false_positive，争议走 adjudication（model_right/gt_right/both/neither） |
| **暂存 / 提交** | 标注两态：暂存写 draft 可反悔，提交才落 result |
| **合理带** | 虚构投标人/业绩/规模"像不像真的"的可接受区间，由专家判断（plaus 区） |

## 编号系统

所有实体统一编号，编号只增不改、不复用。

| 前缀 | 格式 | 实体 |
|---|---|---|
| `TDR` | `TDR-CCGP-{YYYY}-{NNNNN}` | tender 招标项目（爬虫按年递增分配） |
| `RBC` | `RBC-{tdr_id}-v{n}` / `RBC-TPL-{NNN}` | rubric（项目版 / 模板版） |
| `CASE` | `CASE-{tdr_id}-{variant}` | bid_case 标书案例 |
| `INJ` | `INJ-{case_id}-{err_code}-{seq}` | injection 注入偏差 |
| `ERR` | `ERR-{类目}-{NNN}` | err_taxonomy 错误类型 |
| `RUN` | `RUN-{date}-{model}-{caseset}` | run 评测批次 |

状态机：`injection.gt_status` auto→needs_review→confirmed|rejected；
`bid_case.status` baseline→injected→evaluable|retired；
`review_check.result` NULL→pass|fail（专家区存 verdict 文案）；
`finding.verdict` hit|miss|false_positive，争议走 adj_status。

## 平台结构

- **项目总览** `/tenders` — 标注入口：类别卡（工程/货物/服务，规则自动分类）→ 项目 → 三类标注任务（节点+环境 / 专家校验 / 规则标注），实时待审数
- **标注视图** `/case/{id}` — 生成节点 N1-N4 审核卡 + 环境文件（含证据绿/噪声红/普通灰，PDF 阅读器按页反馈）
- **专家校验** `/case/{id}/expert` — 四区判定：点选高亮 → 上一条/暂存/提交/下一条
- **规则标注** `/rubrics/{id}/annotate` — rubric 条目同款标注：保留/改写（文本直接写回）/删除
- **规则编辑** `/rubrics` — rubric 库、条目编辑、模板绑定项目
- 辅助队列：GT 校验 `/queue/gt`、裁决 `/queue/adjudication`、附件校准 `/queue/attachments`
