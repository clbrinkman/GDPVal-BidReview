# 生成 Prompt 集

标书构造流水线的三组 prompt：**P1 rubric 抽取 → P2 基线标书生成 → P3 偏差注入**。
变量用 `{{大括号}}` 标记，运行时替换。输出全部要求结构化（JSON / 固定章节），便于平台落库与校验。

---

## P1. rubric 抽取（招标文件 → delta 条目）

> 对应平台：rubric_item（layer=delta），产出进「规则标注」人工校验后才生效。

```text
你是政府采购评标专家。从下面的招标文件中抽取可用于审查投标文件的规则条目。

【招标文件】
{{tender_detail}}

【抽取要求】
1. 只抽"可判定"的条款：能用 满足/不满足 或 有无 判定的才算；流程说明、联系方式、
   平台操作指引等叙述性文字不抽。
2. 四类归属：
   - qualification 资质：投标资格、证明材料要求
   - compliance 符合性：报价限价、期限、有效期、签署形式等实质性响应要求
   - rejection 废标条款：明确写了"无效投标/废标/拒绝/不接受"的情形，含 ★ 条款
   - score 打分项：评标办法中给分的维度（有分值带分值，没给分值注明"分值待定"）
3. 每条必须给出原文出处 source_ref（章节名或原文短句，供人工跳转核对）。
4. 金额、期限、数量、日期原样保留，不得改写或四舍五入。
5. requirement 写成一条独立的审查指令（"投标报价不得超过预算 ¥X"），
  check_hint 写判定提示（"核对报价一览表总价"）。

【输出】严格输出 JSON 数组，不要输出任何其他文字：
[{"layer":"delta","category":"qualification|compliance|rejection|score",
  "requirement":"...","check_hint":"...","source_ref":"..."}]
```

## P2. 基线标书生成（rubric → 合规标书）

> 对应平台：bid_case（status=baseline），产出过 N1-N4 节点审核后进入注入。
> 关键约束：**基线必须本身合规**，否则注入偏差失去参照系。

```text
你是投标文件编制专家。根据招标文件和审查规则，生成一份"应当通过审查"的基线投标文件。

【招标文件】
{{tender_detail}}

【审查规则（必须逐条满足）】
{{rubric_items}}

【投标人档案（虚构，须全文一致使用）】
{{bidder_profile}}
# bidder_profile 由平台生成：公司名称/成立年限/注册资本/员工数/资质证书/同类业绩，
# 规模须落在该项目的"合理带"内（由专家 plaus 区校准过）

【生成要求】
1. 章节结构：一、资格证明文件；二、商务部分（投标函/报价一览表/商务条款应答）；
   三、技术部分（需求逐条应答 + 实施方案）；四、售后服务与承诺。
2. 逐条应答：审查规则的每一条都要在对应章节有明确响应，应答格式
  "【满足】+ 具体响应内容"，不得笼统写"完全响应招标文件要求"。
3. 硬约束（违反即失败）：
   - 总报价 ≤ 预算/最高限价，且大小写金额一致
   - 服务期/交付期/投标有效期不短于要求
   - 不出现任何占位符（{{}}/【待填】/XXX公司）
   - 公司名称、报价、期限在全文任何位置出现都一致
4. 法规引用只准用真实存在的条文（如《政府采购法》第二十二条），
   不确定的不要引用。
5. 证书/截图类材料：正文写"（附：{{材料名}}，扫描件）"，并单独输出一份
  【扫描件清单】：材料名/应包含的关键字段（如 ISO9001：证书编号、有效期至、发证机构），
  供扫描件构造器渲染。
6. 篇幅：全文 3000-6000 字，技术方案部分不低于 40%。

【输出】先输出标书全文（markdown，章节用一/二/三/四），
然后输出【扫描件清单】JSON 数组。
```

## P3. 偏差注入（基线 + err_code → 注入点 + GT）

> 对应平台：injection（method=G），产出过专家 inj 区"像不像真实偏差"校验。
> P 方式（程序化：日期/金额/有无的机械篡改）不需要 prompt，走规则脚本；
> prompt 只用于需要语义改写的 G 方式。

```text
你是投标文件审查专家，现在要为评测构造一个"真实投标人会犯的错"。

【基线标书片段】
{{baseline_excerpt}}

【要注入的错误类型】{{err_code}} {{err_name}}：{{err_description}}
【真实废标案例参考（对齐分布用）】{{real_case_examples}}

【注入要求】
1. 像真错：这个错误必须以真实投标中常见的形态出现（参考真实案例），
   不能一眼假（如金额写成负数）、不能超出真实分布（如资质过期 9 个月——
   真实多见 1~3 个月）。
2. 单点：只改一处，不扩散修改其他段落；错误点与全文其余内容产生的
   "不一致"正是要被模型检出的信号，不要顺手把其他地方也改一致了。
3. 隐蔽性分级 {{human_level}}：L1 对照条款即可发现；L2 需要跨章节比对；
   L3 需要计算或外部知识（法条时效、划型标准）。
4. before_text 必须是基线原文的精确子串（逐字，供程序化替换定位）；
   after_text 保持上下文通顺自然。

【输出】严格输出 JSON，不要输出任何其他文字：
{"err_code":"{{err_code}}","locator":"章节/表格位置",
 "before_text":"...","after_text":"...",
 "expected_finding":"合格审查模型应当给出的结论（一句话）",
 "plausibility_note":"这个错在真实投标中的常见形态说明（供专家校验参考）"}
```

## P4. 注入自检（可选，G 注入后自动验 GT）

```text
你是评标委员会审查员。只看到下面这份投标文件，不知道任何构造背景。
请逐项对照审查规则列出你发现的所有问题。

【投标文件（已注入偏差）】
{{injected_bid}}
【审查规则】
{{rubric_items}}

【输出】JSON 数组：[{"finding":"问题描述","location":"章节","rule":"对应规则"}]

# 用法：把输出与注入的 expected_finding 对比——能被盲审查出 = GT 可检出（自检通过）；
# 查不出 = 注入太隐蔽或没造成可观察的不一致，回炉重注入。
```

---

## 备注

- 三组 prompt 的产出都落进平台的人工校验闭环：P1 → 规则标注（保留/改写/删除）；
  P2 → N1-N4 节点审核；P3 → 专家 inj 区 + N3 GT 校验。**prompt 生成 ≠ 直接入库**。
- 虚构投标人档案（bidder_profile）单独由平台按合理带规则生成，不交给 LLM 自由发挥。
- 扫描件渲染（把 P2 的【扫描件清单】做成图）走参数化做旧脚本，不走 LLM。
